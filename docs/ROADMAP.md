# 버들여울의 하루 (가제) 개발 로드맵

버전 0.1. 기준 문서는 docs/GDD.md와 docs/TECH_DESIGN.md이다.

# 0. 로드맵 사용법

- 모든 단계는 실행해서 눈으로 확인할 수 있는 결과물 하나로 끝난다. 눈으로 볼 수 없는 작업(타입만 정의, 함수만 작성)은 별도 단계로 두지 않고 화면에서 확인되는 단계에 묶었다.
- 각 단계의 항목
  - 목표: 이 단계가 끝나면 무엇이 보이는가
  - 만들 파일: 새로 만들거나 크게 고치는 파일
  - 완료 조건: 이 조건을 모두 만족해야 다음 단계로 간다
  - 난이도: 하, 중, 상 중 하나. 처음 해보는 사람 기준이며 이유를 한 줄 덧붙였다
- 단계는 앞 단계가 끝나야 시작한다. 순서가 중요한 이유는 각 단계가 이전 단계의 화면 위에 쌓이기 때문이다.
- 각 단계가 끝나면 커밋하고 실제 기기에서 다시 실행해 본다. 시뮬레이터에서만 확인하고 넘어가지 않는다.
- 단계 번호는 M0부터 M17까지이며 여섯 개 구간으로 묶는다.
  - 구간 A, 기반: M0에서 M2
  - 구간 B, 엔진: M3에서 M6
  - 구간 C, 게임 루프: M7에서 M9
  - 구간 D, 깊이: M10에서 M12
  - 구간 E, 연출과 편의: M13에서 M15
  - 구간 F, 콘텐츠와 출시: M16에서 M17

# 구간 A. 기반

## M0. Expo 프로젝트 생성, iPhone과 Galaxy에서 실행 확인

목표: 빈 앱이 개발 PC, iPhone, Galaxy 세 곳에서 똑같이 "버들여울" 문구를 띄운다.

준비물
- Node.js LTS, Git, 코드 에디터
- iPhone과 Galaxy에 Expo Go 앱 설치(App Store, Play Store)
- 개발 PC와 두 폰이 같은 Wi-Fi에 연결되어 있을 것

작업 순서
1. create-expo-app으로 TypeScript와 expo-router가 포함된 템플릿으로 프로젝트를 만든다.
2. 템플릿의 예제 화면을 지우고 화면 중앙에 제목 텍스트 하나만 남긴다.
3. 개발 서버를 켜고 터미널에 뜨는 QR 코드를 읽는다. iPhone은 기본 카메라 앱, Galaxy는 Expo Go 앱 안의 스캐너를 쓴다.
4. 텍스트를 수정해 저장하면 두 폰에서 즉시 바뀌는지 확인한다(Fast Refresh).
5. 앱 방향을 세로 고정(app.json의 orientation을 portrait)으로 두고 폰을 눕혀도 화면이 돌아가지 않는지 확인한다.

만들 파일
- package.json, app.json, tsconfig.json (템플릿 생성물)
- src/app/_layout.tsx
- src/app/index.tsx (제목 텍스트만)
- .gitignore, README.md (실행 방법 3줄 기록)

완료 조건
- iPhone과 Galaxy 양쪽에서 앱이 열리고 "버들여울" 문구가 보인다.
- 코드를 한 줄 고쳐 저장하면 두 폰 모두 몇 초 안에 반영된다.
- 폰을 눕혀도 세로 화면이 유지된다.
- npx tsc --noEmit 이 에러 없이 끝난다.
- 저장소에 커밋되어 있고 README만 보고 다른 사람이 같은 방법으로 실행할 수 있다.

막힐 수 있는 곳과 해결
- QR을 읽어도 연결되지 않으면 공유기가 기기 간 통신을 막는 경우다. 개발 서버를 tunnel 모드로 실행한다.
- Expo Go가 요구하는 SDK 버전과 프로젝트 SDK가 다르면 열리지 않는다. 앱스토어의 최신 Expo Go에 맞는 템플릿을 쓴다.
- 회사나 학교 Wi-Fi는 막히는 일이 많아 가정용 Wi-Fi나 폰 핫스팟을 쓴다.

난이도: 하. 설치와 연결이 전부이며 코드는 거의 없다. 네트워크 환경 문제만 변수다.

난이도: 하. expo-router의 파일 기반 라우팅 규칙만 익히면 된다.

- 노치가 있는 iPhone과 제스처 바가 있는 Galaxy 모두에서 버튼이 가려지지 않는다.
- 다크 모드 전환 시 글자가 읽힌다.

난이도: 하. 정적인 레이아웃 작업이다. 다만 기기마다 안전 영역 차이를 직접 확인해야 한다.

# 구간 B. 엔진

## M3. 난수와 주사위: 디버그 화면에서 굴려 보기

목표: 숨겨진 디버그 화면에서 2d6을 굴리면 결과가 나오고, 같은 시드는 항상 같은 값이 나온다.

만들 파일
- src/types/core.ts (Stat, Resource, Slot, Season, OutcomeTier 등 공용 타입)
- src/engine/rng.ts (createRng, nextFloat, rollDice)
- tests/engine/rng.test.ts
- src/app/debug/dice.tsx (시드 입력, 굴리기 버튼, 결과 리스트)
- vitest 설정과 test 스크립트 추가

완료 조건
- 디버그 화면에서 시드 123으로 10번 굴린 결과가 앱을 껐다 켜도 항상 같다.
- 시드를 바꾸면 결과가 달라진다.
- 6000번 굴려 합계 7이 약 6분의 1에 가깝게 나오는 통계 확인 버튼이 있다.
- vitest가 통과한다.
- 디버그 화면은 개발 빌드에서만 보이도록 막는다.

난이도: 하. 알고리즘은 짧지만 순수 함수와 상태 반환 방식에 익숙해져야 한다.

## M4. 판정 엔진과 성공률 미리보기

목표: 디버그 화면에서 능력치, 준비, 난이도를 조절하면 성공률과 결과 단계가 실시간으로 바뀐다.

만들 파일
- src/engine/check.ts (computeModifiers, totalModifier, successRate, rollCheck, resolveTier)
- src/types/player.ts, src/types/event.ts (CheckDef 포함)
- tests/engine/check.test.ts
- src/app/debug/check.tsx (슬라이더로 능력치, 준비, 도움, 페널티, 난이도 조절. 성공률 표시와 굴리기 버튼. 결과 단계 5종을 색으로 구분)

완료 조건
- 보정 0, 난이도 7일 때 성공률이 58퍼센트로 표시된다(기획서 확률표와 일치).
- 6과 6은 항상 대성공, 1과 1은 항상 대실패로 나온다.
- 보정 합계가 플러스 7을 넘지 않도록 상한이 걸린다.
- 확률표 전체를 검증하는 단위 테스트가 통과한다.
- 1000번 굴린 결과의 단계별 비율이 이론값과 가깝다.

난이도: 중. 5단계 판정 경계값을 정확히 맞추는 일에 주의가 필요하다.

## M5. 콘텐츠 파이프라인: JSON 이벤트가 화면에 뜬다

목표: JSON으로 쓴 이벤트 3개가 빌드 검증을 통과해 메인 화면의 본문과 선택지로 나타난다.

만들 파일
- src/types/event.ts 완성 (Effect, Requirement, Choice, EventDef)
- src/data/events/daily.json, bond.json, chronicle.json (docs/TECH_DESIGN.md 3장의 예시 3개)
- src/data/items.json, npcs.json (예시에 필요한 최소 항목)
- src/i18n/index.ts, src/i18n/locales/ko/events.json, ui.json
- scripts/build-content.ts (zod 검증, 참조 확인, 텍스트 키 확인, generated/content.json 출력)
- src/content/loader.ts
- package.json에 build-content 스크립트 추가

완료 조건
- build-content를 실행하면 성공 메시지가 나온다.
- 일부러 틀린 JSON(없는 아이템 id 참조, 텍스트 키 누락)을 넣으면 어느 파일 어느 항목이 틀렸는지 알려 주며 실패한다.
- 메인 화면에서 이벤트 선택 버튼을 누르면 예시 이벤트 3개를 차례로 불러 와 본문과 선택지가 한국어로 보인다.
- 선택지에 판정이 있으면 버튼에 M4의 성공률이 붙는다(능력치는 임시 고정값).

난이도: 중. zod 스키마와 참조 검증 스크립트 작성이 처음이면 시간이 걸린다.

## M6. 효과와 결과 처리: 선택하면 숫자가 바뀐다

목표: 선택지를 고르면 주사위가 굴러 결과 문장이 나오고, 상단 상태바의 체력, 돈, 평판 같은 숫자가 실제로 변한다.

만들 파일
- src/types/save.ts (GameState, RngState, SlotContext, PendingRoll)
- src/engine/effects.ts (applyEffect, applyEffects, clampPlayer, resolveDebt)
- src/engine/requirements.ts
- src/engine/resolve.ts (previewChoice, beginChoice, commitChoice)
- src/store/gameStore.ts (zustand. 엔진 호출 액션 pickChoice, confirmResult)
- src/ui/components/ResultCard.tsx (결과 문장과 변화량 표시)
- tests/engine/effects.test.ts, resolve.test.ts

완료 조건
- 예시 이벤트 1에서 장터에 달걀을 파는 선택을 하면 돈이 오르고 평판이 오르고 XP가 쌓이는 것이 화면에 보인다.
- 대실패가 나오면 플래그가 서고 다음 이벤트가 대기열에 들어간다.
- 비용이 부족한 선택지는 비활성화되고 이유가 표시된다.
- 자원은 범위를 벗어나지 않는다(체력 0에서 10, 평판 마이너스 5에서 10).
- 같은 시드와 같은 선택이면 항상 같은 결과가 나온다.
- 엔진 단위 테스트가 통과한다.

난이도: 상. 이 프로젝트에서 가장 중요한 규칙 코드이며 이후 모든 단계의 기반이다. 여기서 시간을 들여 테스트를 촘촘히 만든다.

# 구간 C. 게임 루프

## M7. 하루 루프: 아침, 세 슬롯, 밤 정산

목표: 하루를 처음부터 끝까지 한 번 플레이할 수 있다.

만들 파일
- src/engine/deck.ts (고정 이벤트, 대기열, 가중치 추첨, 활동 카드 구성)
- src/engine/day.ts (startDay, advanceSlot, settleNight)
- src/data/events/daily.json 확장(활동 카드용 일, 거래, 관계, 탐색, 준비, 휴식 이벤트 각 2개 이상, 총 12개 내외)
- src/data/balance.json (체력과 마음 증감, 식량 소비, 일당 수치)
- src/ui/components/NightSettlement.tsx (밤 정산 모달)
- 메인 화면에 오전, 오후, 저녁 슬롯 표시와 날짜 갱신

완료 조건
- 아침 소식, 오전, 오후, 저녁 순으로 슬롯마다 카드 3장에서 4장이 나온다.
- 저녁이 끝나면 밤 정산 모달이 식량 소비와 회복량을 보여 준다.
- 정산 후 다음 날 아침으로 넘어가고 날짜가 하루 올라간다.
- 준비 카드를 쓰면 다음 같은 계열 판정 성공률이 오른 숫자로 표시되고, 쓰고 나면 사라진다.
- 체력이 낮을 때 판정 페널티가 성공률에 반영된다.
- 마음 2를 써서 하루 한 번 재도전을 할 수 있다.

난이도: 중. 처리할 규칙은 많지만 M6의 구조 위에서 하나씩 연결하면 된다.

## M8. 세이브와 로드: 앱을 껐다 켜도 이어진다

목표: 플레이 도중 앱을 완전히 종료하고 다시 열어도 같은 지점에서 이어진다.

만들 파일
- src/save/db.ts, migrations.ts (expo-sqlite 연결과 테이블 생성)
- src/save/saveRepo.ts (슬롯 저장, 불러오기, 삭제, 체크포인트 저장)
- src/save/metaRepo.ts
- 스토어 액션에 자동 저장 연결(선택 확정, 결과 확정, 슬롯 이동, 밤 정산, 앱 백그라운드)
- src/app/index.tsx에 이어하기 버튼, src/app/load.tsx에 슬롯 목록(요약 표시, 삭제)
- tests/save/migration.test.ts (과거 버전 샘플 세이브 보관 시작)

완료 조건
- 주사위를 굴린 직후 앱을 강제 종료하고 다시 열면 같은 결과 화면이 복원된다. 재시작해도 결과를 바꿀 수 없다.
- 타이틀의 이어하기가 가장 최근 슬롯을 연다.
- 불러오기 화면에서 슬롯별 이름, 날짜, 플레이 시간이 보이고 삭제할 수 있다.
- 저장 데이터를 일부러 망가뜨리면 손상 안내가 뜨고 앱이 죽지 않는다.
- iPhone과 Galaxy 모두에서 확인했다.

난이도: 중. SQLite 자체는 쉽지만 저장 시점과 pendingRoll 복원 흐름을 정확히 맞춰야 한다.

## M9. 계절 루프: 20일, 세금, 결산

목표: 한 계절을 처음부터 끝까지 약 30분에 완주하고 결산 화면을 본다. 첫 번째 수직 슬라이스다.

만들 파일
- src/engine/season.ts (startSeason, settleSeason, applySeasonChoice, isSeasonEnd)
- src/app/game/season-start.tsx (지난 계절 요약, 이번 계절 목표와 세금)
- src/app/game/season-result.tsx (세금 납부, 빚 이자, 큰 선택 1회, 성과 정리)
- src/data/events/ 에 봄 시즌 이벤트 30개(일상 20, 인연 6, 위기 2, 고정 메인 2)
- 계절 시작 때 체크포인트 저장
- 디버그 메뉴에 날짜 점프와 자원 수정 기능(테스트 편의)

완료 조건
- 새로 시작해서 봄 20일을 끝까지 플레이할 수 있다.
- 세금을 못 내면 빚이 생기고 결산 화면에 이자가 표시된다.
- 계절 결산 후 다음 계절 시작 화면으로 이어진다.
- 한 번 완주하는 데 걸린 실제 시간을 기록한다. 기록이 30분에서 크게 벗어나면 일수와 슬롯 구성을 조정할 근거로 삼는다.
- 완주 중 앱이 죽거나 막히는 지점이 없다.
- 친구 한 명에게 앱을 건네 설명 없이 한 계절을 해 보게 하고 막힌 곳을 메모한다.

난이도: 중. 구조는 쌓은 것의 조합이지만 처음으로 콘텐츠를 많이 만들어야 해서 분량이 많다.

목표: 플레이하면 능력치가 오르고, 도구가 닳고, 이웃과의 관계 단계가 올라가는 것이 화면에 보인다.

만들 파일

- src/ui/sheets/InventorySheet.tsx, src/app/menu/inventory.tsx (도구 내구도, 식량, 선물 사용)

완료 조건

- 능력치가 오르면 그 능력치용 새 카드가 선택지에 나타난다.
- 도구를 쓰면 내구도가 닳고, 손질 카드로 회복되며, 0이 되면 보너스가 사라진다.

- 판정 보정 합계 상한 플러스 7이 지켜진다.

난이도: 중. 규칙 자체는 단순하지만 화면과 데이터가 동시에 많이 늘어난다.

난이도: 하. 이미 있는 구조에 데이터를 더하는 작업이 중심이다.

완료 조건

난이도: 중. 조건 조합과 우선순위 설계가 핵심이며 콘텐츠 작성량이 늘어난다.

# 구간 F. 콘텐츠와 출시

난이도: 상. 코드보다 글쓰기와 반복 조정이 많은 구간이며 가장 오래 걸린다.

난이도: 상. 코드가 아니라 계정, 인증서, 심사 규정 때문에 막히는 일이 많다. 개발자 계정 가입은 M12 무렵부터 미리 해 둔다.
